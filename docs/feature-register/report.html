What's Broken in Mission Control

Roughly 400 features, checked one at a time against real data. About sixty of them do not do what they say.

How this was checked

Every feature was asked four questions: what it is, what it is expected to do, whether it does that, and how we know. The fourth question is the point.

A passing test was not accepted as proof. Tests here pin current behaviour, and several were found pinning the defect itself, including two written the same week by the author of this report. Where nobody could verify something, the entry says so rather than guessing.

Most findings below came from running the code against live data on the machine, not from reading it. The test suite was green throughout.

Most of the status bugs are one line

The freshness stamp records when we read a file, not when the event happened.

server/statusHookTailer.mjs:114

  agent.hookStatusTs = Date.now();   // the read, not the event

Every record claude writes carries its own timestamp. Nothing reads it. The reader starts at byte zero, so attaching to a fourteen-hour-old feed stamps every historical event as "just now", and the last one wins.

That is why a card sits on WORKING for hours. The same mistake in the sub-agent reader turned 137 old files into "67 agents, all one second old".

Session lifecycle

62 features · 10 broken
01

Pressing K can orphan a claude forever

server/fleet.mjs:229-237measured

Kill sends a terminate signal, then immediately empties the slot. Every force-kill path walks that same slot list, so once the slot is empty the process is unreachable by all of them. A claude that ignores the first signal survives the kill, survives quit, and survives shutdown. The card is gone, so nothing shows it is still running.

Pressing K is worse than force-closing the application.

stand-in claude that ignores SIGTERM

  after K              alive   slot = null
  after killAll()      alive   not in the slot table
  after hardKillAll()  alive   not in the slot table
  after mc clean exit  alive   reparented to launchd
02

A dead session reports IDLE

server/ptyAgent.mjs:673measured

The restart logic only treats a non-zero exit code as a failure. A process killed by a signal reports exit code zero with a signal number, and a clean exit reports zero too. Neither marks the slot as broken and neither triggers a restart.

real child, killed from outside

  after external SIGKILL -> pty: GONE  status = idle  restarts = 0
  tail: process exited code=0 signal=9

all four death routes through the spawn seam

  exit code 0        pty GONE   status idle
  exit code 1 x3     pty GONE   status error   <- the only covered case
  exit SIGKILL       pty GONE   status idle
  working, exit 0    pty GONE   status working
This one is mine. The guard I added on the same day only fires when the restart budget runs out, and the test I wrote for it asserts that a process-less slot is not an error. The test passes and locks in the wrong answer.
03

One session can run in two slots at once

server/fleet.mjs · resume()measured

The same session was accepted into slot 1 and slot 2 with no complaint. The guards check whether a slot is in use, never whether the session is already live somewhere else.

04

A resume that is not a resume still says "resumed"

server/ptyAgent.mjs:419-424traced

When the conversation file is missing, the launch quietly falls back to starting a brand-new empty conversation. The toast still reads resumed, so the user believes their history came back.

05

Un-pausing always reports "working"

server/ptyAgent.mjs:844measured

The status is set unconditionally. A session that was idle before it was paused comes back claiming to be working.

11

The background-agent count was a hardcoded 1, then a wrong 67

server/subagentUsageTailer.mjsmeasured

A file's age was taken from the moment we first looked at it, so 137 historical files all appeared one second old.

before          137 files on disk -> 67 agents, all 0.0s old
after the fix   137 files on disk -> 0 agents       (newest untouched 13.8h)

This one is mine too. I replaced a hardcoded 1 with a confident 67, which is worse because it looks like real data. My test passed because I wrote it against a copy of the logic instead of the real code. Now fixed and verified against both live directories above.

Commands, hotkeys and modals

129 features · 12 broken
12

:resume 12 resumes slot 1 and tells you it worked

tui/App.jsx:1025-1031measured

Any slot number outside 1 to 10 is silently dropped. The argument list becomes empty, so the command falls through to its no-argument form and acts on whatever is focused. The message is affirmative and names a slot the user never typed.

observed on a 20-slot fleet

  :resume 12   -> un-pauses the focused session, toast: "resume slot 1"
  :resume 99   -> same
  :resume abc  -> same

This is the exact defect that was fixed for the kill command in the past, where an out-of-range slot used to kill the focused session. Resume, cap and forget never got the same treatment. The fleet can grow to 64 slots; these three stop at 10.

Zoom and terminal

64 features · 12 broken
14

Scroll does not hold its place

tui/zoom/PtyPane.jsx:515measured

The scroll position is measured from claude's live cursor, which moves down one row for every row claude prints. Park yourself twenty rows back and the output drags you forward until you are at the bottom again, while the indicator still claims you are twenty rows back.

parked 20 rows back, claude keeps printing

  SCROLL 20   window = L062 … L080   user parks here
  SCROLL 20   window = L067 … L085
  SCROLL 20   window = L072 … L090
  SCROLL 20   window = L077 … L095
  SCROLL 20   window = L082 … L100   back at the bottom

The fix needs an anchor that does not move: resolve the offset to an absolute row the moment a scroll key is pressed, and hold it across renders.

15

tui/modals/ShellOverlay.jsx:185-188measured

No offset, no keys, no hint. The file's own note says the five thousand captured rows are unreachable.
